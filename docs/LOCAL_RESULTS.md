## 缓存测量

环境：macOS arm64，本机 Docker；库存容器 1 CPU / 768 MiB，单实例。500 个 SKU；固定 100 请求/秒；每轮 10 秒；并发上限 32；相同数据和确定性请求序列；缓存 TTL 30 秒。每类运行三轮。cold 表示每轮开始清空该实验的缓存，轮内会逐渐预热。

| 轮次 | 平均毫秒 | p95 毫秒 | 失败 | 丢弃 | 说明 |
| --- | ---: | ---: | ---: | ---: | --- |
| off-1 | 2.087 | 2.939 | 0 | 0 | 有并发系统检查，排除比较 |
| off-2 | 1.305 | 2.055 | 0 | 0 | — |
| off-3 | 1.349 | 2.174 | 0 | 0 | — |
| cold-1 | 19.757 | 18.433 | 0 | 30 | 有丢弃，非健康负载 |
| cold-2 | 1.445 | 2.127 | 0 | 0 | — |
| cold-3 | 1.383 | 2.118 | 0 | 0 | — |
| warm-1 | 1.482 | 2.167 | 0 | 0 | — |
| warm-2 | 1.463 | 2.182 | 0 | 0 | — |
| warm-3 | 1.266 | 1.886 | 0 | 0 | — |

平均与分位数仅统计返回正确内容的 HTTP 200 请求。off-1 前约 3.1 秒与系统检查重叠，保留原始数据并排除性能结论。cold-1 有 30 个请求因并发上限丢弃，不能以它的成功延迟代表健康容量。

**这次本机实验没有证明 Redis 能稳定降低响应时间。** 数据量、数据库距离、服务启动状态和负载都会影响结果。暂时可以描述已实现缓存、回源和可复现实验；不能据此写“延迟降低 X%”或生产节日流量成绩。
